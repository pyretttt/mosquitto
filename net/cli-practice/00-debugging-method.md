# A repeatable debugging method

Networking becomes manageable when every command answers one precise question.
Do not change configuration until you can name the failed layer and show
evidence.

## The path model

For a client request, inspect in this order:

```text
name -> socket -> local route -> neighbor -> interface
     -> firewall/conntrack -> path -> remote interface
     -> remote route -> remote firewall -> remote socket
```

The reply must traverse the reverse path. “The request arrived” is only half a
successful exchange.

At each host or router ask:

1. What source and destination should the packet have here?
2. Which route and outgoing interface should the kernel choose?
3. Is the next-hop neighbor reachable?
4. Does a firewall hook accept it?
5. Does the packet enter and leave as predicted?
6. Is a process listening at the destination?
7. Can the reply return?

## The first-pass sequence

Type this sequence until it becomes automatic. Replace addresses and ports with
the real flow.

```bash
# Endpoint configuration and routing decision
ip -br link
ip -br addr
ip route
ip route get 10.20.2.10
ip neigh

# Local service and connection state
ss -lntup
ss -tnp

# One narrow packet observation
tcpdump -ni any -c 20 'host 10.20.2.10 and tcp port 8080'

# Only when a router/firewall is in the path
nft list ruleset
iptables -nvL
conntrack -L
```

`ip netns exec clp-client COMMAND` asks the question from the client. Change
the namespace to `clp-router` or `clp-server` to change the observation point.

## Evidence before fixes

Write a four-line incident note:

```text
Expected:
Observed:
Boundary:
Evidence:
```

Example boundaries are “client creates SYN but router does not forward it” or
“SYN reaches server but no SYN-ACK leaves.” A boundary is more useful than a
guess such as “firewall issue.”

Make one change, rerun the same observation, and undo experimental rules. If
you change routing, firewall, MTU, and service state together, you learn
nothing about causality.

## Failure signatures

- `Network is unreachable`: no matching route at the sending host.
- `No route to host`: often a route or neighbor failure, but may also be an
  ICMP reject generated by a firewall. Capture to distinguish them.
- Immediate `Connection refused`: the destination replied with TCP RST;
  routing works, but no listener accepted that address/port or a firewall
  rejected it.
- Timeout with repeated SYNs: request or reply is silently dropped.
- TCP handshake succeeds but data stalls: inspect MTU/PMTUD, window state,
  retransmissions, and application behavior.
- Ping succeeds but the application fails: ICMP and the application's
  protocol/port follow different policy and service paths.
- One direction works: inspect the return route, stateful policy, NAT state,
  and asymmetric routing.

## Drill

Run the topology and services:

```bash
./scripts/setup-routed.sh
./scripts/setup-services.sh
```

Without using `ping` first, prove all of the following:

1. The client would send `10.20.2.10` through the router.
2. The router has a route for both endpoint addresses.
3. TCP/8080 is listening in the server namespace.
4. A TCP handshake crosses both router interfaces.
5. The client and server agree on the connection's four-tuple.

Use the relevant tool module when you do not know a command. Reset afterward:

```bash
./scripts/reset.sh
```
