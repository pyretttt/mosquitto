# `ss`: sockets and TCP state

`ss` answers host-local questions. It cannot prove that a packet crossed a
wire; `tcpdump` does that. Use `ss` first when the symptom names a port,
listener, process, or TCP state.

## Where you are

You can prove that a namespace has an address, a route, and a neighbor.
This module is the next question: **is a process actually bound to the
port we think**, and **what is the kernel's TCP state machine doing?**

## What you need, and what you do not

Need: foundations on ports, four-tuples, and the TCP handshake;
[`ip`](02-ip.md) so you can sit in the right namespace.

Do not need: congestion-control algorithms (CUBIC, BBR) by name. `ss -ti`
will show `cwnd` and `rtt`; treat them as "is the sender blocked by the
network or by the application?" until the performance module.

## Mental model

A listening socket has a local address and port, and no peer yet. A
connected TCP socket has a four-tuple:

```text
source address : source port → destination address : destination port
```

The client's four-tuple and the server's four-tuple are the same
conversation seen from opposite ends. If they disagree, you are not looking
at the same flow — or NAT is rewriting addresses, which is module 8.

Important TCP states, with the question each one answers:

| State | Who is in it | Meaning |
|-------|----------------|---------|
| `LISTEN` | server | Waiting for new handshakes on a local port. |
| `SYN-SENT` | client | SYN went out; no valid SYN-ACK yet. Routing or filtering may still be broken. |
| `SYN-RECV` | server | SYN arrived, SYN-ACK sent, final ACK not seen. Return path or client trouble. |
| `ESTAB` | both | Handshake completed. Data may still be stuck. |
| `TIME-WAIT` | the side that closed first | Healthy leftover: hold the tuple so a delayed segment cannot attach to a new connection. |

Queues mean different things by state. On an established socket, `Recv-Q`
means bytes the application has not read and `Send-Q` means bytes not yet
acknowledged. On a listener they represent pending handshakes and the
configured backlog. A huge `Recv-Q` is often a slow application, not a
slow network.

### Bind address is a reachability claim

The listener's local address is part of the diagnosis:

- `0.0.0.0:8080` — all IPv4 interfaces in this namespace.
- `10.20.2.10:8080` — only that address.
- `127.0.0.1:8080` — only loopback; the client on another namespace will
  never reach it, even if routing is perfect.

`ss` is how you prove this. Guessing from the service command line is how
you get it wrong.

## Option anatomy

`ss` commonly combines short options:

```text
-t TCP        -u UDP       -l listening       -a all
-n numeric    -p process   -i TCP internals   -o timers
-4 IPv4       -6 IPv6      -s summary
```

Build from a question:

```bash
ss -lntp                     # listening TCP, numeric, process
ss -lunp                     # listening UDP, numeric, process
ss -tan                      # every TCP state
ss -tin                      # established TCP internals
ss -s                        # protocol/state summary
```

Inside this lab, select an observation point:

```bash
ip netns exec clp-server ss -lntp
```

Without `ip netns exec`, you are asking the container root, which is not
the server.

## Filter anatomy

Filters come after options. Quote expressions containing parentheses.

```bash
ss -tn state established
ss -tn state syn-sent
ss -tn sport = :8080
ss -tn dport = :8080
ss -tn dst 10.20.2.10
ss -tn '( dport = :80 or dport = :8080 )'
```

`sport` and `dport` are interpreted from the namespace where `ss` runs. On
the server, port 8080 is usually the source/local port; on the client it is
the destination/peer port. If a filter returns nothing, reverse source and
destination before concluding the socket does not exist.

## TCP internals

```bash
ss -tin dport = :8080
```

Useful fields include:

- `rtt` and `minrtt`: current smoothed versus best observed round-trip
  time;
- `cwnd`: congestion window in segments;
- `rto`: retransmission timeout;
- `retrans`: retransmission history/current retransmissions;
- `bytes_sent`, `bytes_acked`, `bytes_received`;
- `send` or `delivery_rate`;
- `pmtu`, `mss`, and `advmss`;
- `app_limited`: the application, not the network, supplied too little
  data.

A single snapshot is not a trend. Compare observations during a controlled
transfer.

## Common misconceptions

- **"`ss` shows ESTAB, so the application works."** The handshake can
  succeed while HTTP stays on a different port, or the process can hang
  after accept.
- **"`Connection refused` means a firewall."** Refused is usually a RST
  from a host that received the SYN. Timeouts are the silent-drop
  signature. Confirm with `ss -lntp` and a capture.
- **"I killed the server, so the port is free."** `TIME-WAIT` or a child
  process may still own the tuple. Look at `ss -tanp`.

### Possible gap: UDP, Unix sockets, and other families

`ss -u` lists UDP. `ss -x` lists Unix domain sockets (same-host, no IP).
This track stays on TCP/IPv4 because the incidents are TCP/IPv4. The
grammar transfers.

```bash
./scripts/setup-routed.sh
./scripts/setup-services.sh

ip netns exec clp-server ss -lntp
ip netns exec clp-server ss -lntp sport = :8080
ip netns exec clp-server ss -lntp sport = :5201
ip netns exec clp-client curl -s http://10.20.2.10:8080/ >/dev/null
ip netns exec clp-client ss -tan
```

Create a connection long enough to observe:

```bash
ip netns exec clp-client iperf3 -c 10.20.2.10 -t 20
```

While it runs, use a second shell (`./lab.sh shell` from macOS) and answer:

1. What is the client's ephemeral port?
2. What four-tuple does the server report?
3. What are the client's RTT, congestion window, and retransmission count?
4. Does either side have a persistent nonzero send or receive queue?

Stop the HTTP server process, attempt a connection, and explain the
difference between "refused" and "timed out." Restore services with
`./scripts/setup-services.sh`.

## Retrieval test

Without notes, write commands to:

- identify the process listening on TCP/8080;
- show all TCP sockets, including listening and `TIME-WAIT`;
- show only `SYN-SENT`;
- inspect RTT and retransmissions for traffic to TCP/5201;
- prove whether a service bound only to loopback.

The last question requires reading the listener's local address:
`127.0.0.1`, `10.20.2.10`, or `0.0.0.0` have different reachability.
