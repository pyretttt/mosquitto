# `ip`: interfaces, addresses, neighbors, routes

Use `ip` to inspect or change the kernel's network configuration. Its stable
grammar is:

```text
ip [global options] OBJECT VERB [object-specific arguments]
```

Read commands left to right: “IP, in namespace client, route, get destination.”

```bash
ip -n clp-client route get 10.20.2.10
```

`-n NAME` works for `ip` commands. To run another program in a namespace, use
`ip netns exec NAME PROGRAM`.

## Mental model

- A **link** is an interface and its L2 properties: state, MAC, MTU, counters.
- An **address** is an L3 identity attached to a link.
- A **neighbor** maps an on-link IP address to an L2 address using ARP or NDP.
- A **route** maps a destination prefix to a next hop and/or output link.
- A **rule** selects a routing table. Most labs use the main table.

The kernel first performs longest-prefix match. A directly connected `/24`
beats a default `/0`; a host `/32` beats both. The next hop must itself be
reachable through an on-link route.

## Observation anatomy

```bash
ip -br link                    # brief link inventory
ip -s link show dev c-eth0     # counters for one link
ip -d link show dev c-eth0     # link type and detailed attributes

ip -br -4 addr                 # compact IPv4 addresses
ip -6 addr show dev eth0       # IPv6 addresses on one link

ip neigh show                  # ARP and NDP cache
ip neigh show nud failed       # unresolved neighbors

ip route show                  # main IPv4 table
ip route show table all        # every table
ip route get 10.20.2.10        # actual lookup, including source selection
ip -6 route get fd00::10
ip rule show                   # policy-routing rule order
```

Prefer `-br` for inventory and full output for investigation. Prefer
`route get` over visually guessing which route matches.

## Mutation anatomy

```text
ip link set dev DEVICE up|down|mtu NUMBER
ip addr add|del PREFIX dev DEVICE
ip route add|replace|del PREFIX via NEXT_HOP dev DEVICE
```

Examples:

```bash
ip -n clp-client link set dev c-eth0 up
ip -n clp-client addr add 10.20.1.10/24 dev c-eth0
ip -n clp-client route replace default via 10.20.1.1
ip -n clp-client route add blackhole 203.0.113.0/24
```

Use `replace` while iterating on a route that may already exist. Use `add` when
an existing route should be treated as an error.

## Namespace and veth anatomy

A veth pair is a virtual cable: a frame transmitted at one end arrives at the
other. Moving each end into a namespace creates a link between virtual hosts.

```bash
ip netns add left
ip netns add right
ip link add left0 type veth peer name right0
ip link set left0 netns left
ip link set right0 netns right
```

The lab scripts build this for you, but once per week rebuild the main topology
by hand from `scripts/setup-routed.sh`, then delete only your temporary
namespaces.

## Muscle-memory drill

Start the routed lab. Predict each answer before typing:

```bash
./scripts/setup-routed.sh

ip netns list
ip -n clp-client -br link
ip -n clp-client -br addr
ip -n clp-client route
ip -n clp-client route get 10.20.2.10
ip -n clp-router route get 10.20.2.10
ip -n clp-server route get 10.20.1.10
ip -n clp-client neigh
ip netns exec clp-client ping -c 1 10.20.2.10
ip -n clp-client neigh
ip -n clp-client -s link show dev c-eth0
```

Now break and restore three different layers:

1. Set `c-eth0` down. Identify the changed link flags, restore it, and verify.
2. Delete the client default route. Use `route get` to prove the failure, then
   restore the route.
3. Change the server prefix length to `/32`. Explain why its default next hop
   is no longer considered on-link, then restore `/24`.

Do not use the setup script to repair these. Use `ip`.
