# `ip`: interfaces, addresses, neighbors, routes

Use `ip` to inspect or change the kernel's network configuration. Every
later tool assumes this picture is correct. If the route is wrong, a
beautiful `tcpdump` filter will capture silence.

## Where you are

You know why the lab has two `/24`s, why the router has two addresses, and
why the return path is a separate lookup. This module is how the Linux
kernel stores those facts, and how you read them.

## What you need, and what you do not

Need: [foundations](00-foundations.md) §§3–7 and the
[debugging method](01-debugging-method.md).

Do not need: policy routing, VRFs, or multiple routing tables. They exist;
this lab uses the **main** table. `ip rule` is shown so you can see that a
deeper mechanism is there, not so you must design one.

## Mental model

The kernel answers four questions, in roughly this order, before a packet
can leave a host:

1. **Link** — Is there an interface, and is it up? A link is the L2 object:
   name, state, MAC, MTU, counters.
2. **Address** — Which L3 identities are attached to that link?
3. **Route** — For this destination IP, which interface and next hop?
4. **Neighbor** — If the next hop is on-link, which MAC?

A **rule** (`ip rule`) selects which routing table to consult. Most
systems, and this lab, use the main table. If `ip route get` ever
disagrees with `ip route show`, you have left the simple case; list rules
before inventing a new route.

### How a lookup actually works

Given destination `10.20.2.10` on the client:

1. Longest prefix match in the routing table. A connected `10.20.1.0/24`
   does **not** match `10.20.2.10`. The default `0.0.0.0/0` via
   `10.20.1.1` does.
2. The next hop `10.20.1.1` must itself be reachable by an **on-link**
   route (the connected `/24` on `c-eth0`). The kernel then ARPs for
   `10.20.1.1`, not for `10.20.2.10`.
3. Source address selection picks `10.20.1.10` because that is the address
   on the outgoing interface. `ip route get` shows this; eyeballing
   `ip route` does not always.

A directly connected `/24` beats a default `/0`. A host `/32` beats both.
That is **longest prefix match**: more specific wins.

If you change the server's prefix to `/32`, the kernel no longer treats
`10.20.2.1` as on-link, so the default route's next hop is unreachable even
though the cable is fine. The drill at the end makes you feel this. It is
the same bug as "I assigned an address without a subnet mask" on a real
NIC.

### Link flags worth reading

`ip link` prints flags such as `UP` and `LOWER_UP`. `UP` is the admin
state you set. `LOWER_UP` means the virtual (or physical) carrier is
present. A veth with the peer deleted can be `UP` and still be useless.
Counters (`RX`/`TX`, errors, dropped) are evidence; a quiet interface
during a test means the packet never got here.

## Command grammar

Stable grammar:

```text
ip [global options] OBJECT VERB [object-specific arguments]
```

Read left to right: "IP, in namespace client, route, get destination."

```bash
ip -n clp-client route get 10.20.2.10
```

`-n NAME` works for `ip` itself. To run another program in a namespace,
use `ip netns exec NAME PROGRAM`.

## Observation anatomy

```bash
ip -br link                    # brief link inventory
ip -s link show dev c-eth0     # counters for one link
ip -d link show dev c-eth0     # link type and detailed attributes

ip -br -4 addr                 # compact IPv4 addresses
ip -6 addr show dev eth0       # IPv6 addresses on one link

ip neigh show                  # ARP and NDP cache
ip neigh show nud failed       # unresolved neighbors

ip route show                  # main IPv4 table
ip route show table all        # every table
ip route get 10.20.2.10        # actual lookup, including source selection
ip -6 route get fd00::10
ip rule show                   # policy-routing rule order
```

Prefer `-br` for inventory and full output for investigation. Prefer
`route get` over visually guessing which route matches. `route get` is
the kernel's answer to "what would I do with this packet right now?"

## Mutation anatomy

```text
ip link set dev DEVICE up|down|mtu NUMBER
ip addr add|del PREFIX dev DEVICE
ip route add|replace|del PREFIX via NEXT_HOP dev DEVICE
```

Examples:

```bash
ip -n clp-client link set dev c-eth0 up
ip -n clp-client addr add 10.20.1.10/24 dev c-eth0
ip -n clp-client route replace default via 10.20.1.1
ip -n clp-client route add blackhole 203.0.113.0/24
```

Use `replace` while iterating on a route that may already exist. Use `add`
when an existing route should be treated as an error. Always include the
prefix length on `addr add`; `10.20.1.10` without `/24` is a `/32` on
modern `ip` and will break on-link detection.

## Namespace and veth anatomy

A veth pair is a virtual cable: a frame transmitted at one end arrives at
the other. Moving each end into a namespace creates a link between virtual
hosts.

```bash
ip netns add left
ip netns add right
ip link add left0 type veth peer name right0
ip link set left0 netns left
ip link set right0 netns right
```

The lab scripts build this for you, but once per week rebuild the main
topology by hand from `scripts/setup-routed.sh`, then delete only your
temporary namespaces. Reading the script after you can predict each line is
a better exercise than reading it first.

## Common misconceptions

- **"The router has a route, so the client is fine."** Each namespace has
  its own table. Prove `route get` at the sender **and** at the responder.
- **"I pinged the gateway, so the default route works."** Pinging
  `10.20.1.1` only proves the left subnet. The client still needs a
  default (or a more specific) route to `10.20.2.0/24`.
- **"No packets in tcpdump means the network is down."** If `route get`
  fails, the kernel never sent a frame. That is a routing bug, not a
  capture bug.
- **"I'll add a second default route."** Two defaults without metrics
  fight. `replace` the one you mean.

### Possible gap: IPv6, policy routing, VRFs

`ip -6` is the same objects with different addresses. Rules and tables
(`ip rule add … table 100`) appear when a host must choose routes by
source address or interface — common in multi-homed servers. VRFs isolate
whole routing worlds. You can finish this track without them. If
`ip route get` cites an unexpected table, `ip rule show` is the next
command, not a new default route.

## Muscle-memory drill

Start the routed lab. Predict each answer before typing:

```bash
./scripts/setup-routed.sh

ip netns list
ip -n clp-client -br link
ip -n clp-client -br addr
ip -n clp-client route
ip -n clp-client route get 10.20.2.10
ip -n clp-router route get 10.20.2.10
ip -n clp-server route get 10.20.1.10
ip -n clp-client neigh
ip netns exec clp-client ping -c 1 10.20.2.10
ip -n clp-client neigh
ip -n clp-client -s link show dev c-eth0
```

Notice that neighbor entries appear **after** the ping. ARP is demand-driven.

Now break and restore three different layers:

1. Set `c-eth0` down. Identify the changed link flags, restore it, and
   verify.
2. Delete the client default route. Use `route get` to prove the failure,
   then restore the route.
3. Change the server prefix length to `/32`. Explain why its default next
   hop is no longer considered on-link, then restore `/24`.

Do not use the setup script to repair these. Use `ip`.
