# A repeatable debugging method

Networking becomes manageable when every command answers one precise
question. Do not change configuration until you can name the failed layer
and show evidence.

## Where you are

You can walk a ping across the lab in words: two subnets, a forwarding
router, ARP per cable, a return route. This module turns that story into a
ritual you will reuse for every tool and incident.

## What you need, and what you do not

Need: [foundations](00-foundations.md), especially the failure map and
`ip netns exec`.

Do not need: fluency with `ss`, `tcpdump`, or firewalls yet. The first-pass
sequence below **shows** those commands so you know they exist. Type them
once after setup; treat anything you cannot read as a pointer to a later
module, not as a failure.

## The path model

For a client request, inspect in this order:

```text
name → socket → local route → neighbor → interface
     → firewall/conntrack → path → remote interface
     → remote route → remote firewall → remote socket
```

This lab has no DNS names, so skip **name** until a real incident gives you
a hostname. The reply must traverse the reverse path. "The request arrived"
is only half a successful exchange.

At each host or router ask:

1. What source and destination should the packet have here?
2. Which route and outgoing interface should the kernel choose?
3. Is the next-hop neighbor reachable?
4. Does a firewall hook accept it?
5. Does the packet enter and leave as predicted?
6. Is a process listening at the destination?
7. Can the reply return?

Write the answers **before** you type. A wrong prediction plus a surprising
command output is learning. A command typed without a prediction is noise.

## Observation points are not interchangeable

The same flow is a different object at each place:

```text
clp-client / c-eth0
    → clp-router / r-left
    → clp-router / r-right
    → clp-server / s-eth0
```

`ip netns exec clp-client COMMAND` asks the question from the client.
Change the namespace to `clp-router` or `clp-server` to change the
observation point. On the router, also choose **which interface** you
capture. "I ran tcpdump" is not evidence until you can say where.

A process running in the container's root namespace is not on the client.
`ss` without `ip netns exec` will show the container's own sockets, which
in this lab are usually uninteresting.

## The first-pass sequence

Type this sequence until it becomes automatic. Replace addresses and ports
with the real flow.

```bash
# Endpoint configuration and routing decision
ip -br link
ip -br addr
ip route
ip route get 10.20.2.10
ip neigh

# Local service and connection state
ss -lntup
ss -tnp

# One narrow packet observation
tcpdump -ni any -c 20 'host 10.20.2.10 and tcp port 8080'

# Only when a router/firewall is in the path
nft list ruleset
iptables -nvL
conntrack -L
```

From the client that becomes:

```bash
ip netns exec clp-client ip -br addr
ip netns exec clp-client ip route get 10.20.2.10
```

or, for `ip` only, the short form:

```bash
ip -n clp-client route get 10.20.2.10
```

You are not expected to interpret every line yet. You are expected to know
**why** this order exists: configuration, then sockets, then the wire, then
policy.

## Evidence before fixes

Write a four-line incident note:

```text
Expected:
Observed:
Boundary:
Evidence:
```

**Expected** is a packet story: "client SYN from `10.20.1.10` to
`10.20.2.10:8080` via `10.20.1.1`, forwarded out `r-right`, accepted by a
listener, SYN-ACK returns."

**Observed** is a symptom with a command: `curl: (28) Connection timed out`
after two seconds.

**Boundary** is the first adjacent pair of observation points that
disagree. Example: "SYN leaves `r-left`, SYN never leaves `r-right`." That
is more useful than "firewall issue."

**Evidence** is the output that forced the boundary on you: a capture, a
route lookup, a rule counter.

Worked example of a good note:

```text
Expected: client reaches 10.20.2.10:8080 through the router; server
          replies via 10.20.2.1
Observed: curl times out; ping also fails from client to server
Boundary: client route get succeeds; server has no route to 10.20.1.10
Evidence: ip -n clp-server route get 10.20.1.10 → Network unreachable
```

Make one change, rerun the **same** observation, and undo experimental
rules. If you change routing, firewall, MTU, and service state together,
you learn nothing about causality.

## Failure signatures

These are starting hypotheses, not diagnoses. Each one still needs a
boundary.

- `Network is unreachable`: no matching route at the sending host. The
  kernel never built a frame. A capture on that host's NIC can be empty
  **and still be consistent**.
- `No route to host`: often a route or neighbor failure, but may also be
  an ICMP reject generated by a firewall. Capture to distinguish them.
- Immediate `Connection refused`: the destination (or a device pretending
  to be it) replied with TCP RST. Routing worked far enough for a response
  to return. Usually: no listener on that address/port, or a reject rule.
- Timeout with repeated SYNs: request or reply is silently dropped.
  Distinguish "SYN never leaves the client" from "SYN dies in the router"
  from "SYN-ACK dies on the way back" by moving the capture point.
- TCP handshake succeeds but data stalls: inspect MTU/PMTUD, window
  state, retransmissions, and application behavior. This track only
  sketches PMTUD; see the gap below.
- Ping succeeds but the application fails: ICMP and the application's
  protocol/port follow different policy and service paths.
- One direction works: inspect the return route, stateful policy, NAT
  state, and asymmetric routing.

### Possible gap: PMTUD and "large transfer hangs"

If small pings and a TCP handshake work but a large HTTP body hangs, the
path MTU may be smaller than the endpoints believe, and ICMP
"Fragmentation Needed" may be filtered. The parent `net/` week 7 lab
reproduces that. You do not need to master it to finish these incidents.
If you see that signature, capture ICMP unreachable messages and compare
interface MTUs with `ip link`.

## What this method refuses to do

It does not start with "restart the service." It does not treat `ping`
as a complete test of an HTTP path. It does not debug from the middle of
the Internet inward; it starts at the endpoints you control and walks
toward the first disagreement.

Production adds change history, DNS, TLS, load balancers, and permission
to capture. The ritual is the same: define the flow, pick an observation
point, find the first failed boundary, prove the fix.


Without using `ping` first, prove all of the following:

1. The client would send `10.20.2.10` through the router.

4. A TCP handshake crosses both router interfaces.
